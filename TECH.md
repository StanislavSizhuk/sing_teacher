numba-коду `librosa`. Python — це оркестрація на кількасот рядків. Виграш дають
заміна раннтаймів, алгоритмічні обмеження й кешування, а не мова обгортки.

## 1. Огляд і цілі

Веб-застосунок, що аналізує спів користувача порівняно з оригінальним вокалом
пісні та дає детальний фідбек: точність нот, ритм, вібрато, дихання/фразування,
динаміка гучності, тембр.

Аналіз виконується постфактум (не в реальному часі). Увесь стек розгортається
однією командою `docker compose up` на одному VPS.

Користувач обирає один із двох режимів запису:

- **`clean`** — акапельний спів у навушниках, без супроводу. Дає повний аналіз
  за всіма 6 аспектами й найвищу точність.
- **`mixed`** — спів під супровід (власна гітара, піано, бенд, мінус, пісня з
  колонок). Аналізуються 4 аспекти з 6; точність нижча, і це явно позначено в
  звіті.

**Стек:** Go (API-шар) + Python (ML/аудіо) + React (фронтенд) + PostgreSQL +
Redis + Caddy, усе в Docker Compose.

### 1.1 Цілі

| # | Ціль | Як вимірюється |
|---|---|---|
| G1 | Користувач отримує об'єктивну оцінку співу за 6 аспектами | Аналіз повертає під-оцінки + загальний бал (0–100); у `mixed` недоступні аспекти позначені `null` із причиною |
| G2 | Фідбек зрозумілий не-музиканту | Текстовий звіт із конкретними порадами, а не сирі числа |
| G3 | Розгортання в одну команду | `docker compose up` на чистому VPS піднімає робочий стек |
| G4 | Прогрес видно в часі | Графік `overall_score` по датах, з розрізненням режимів |
| G5 | Проект підтримуваний одним розробником | Бус-фактор компенсується документацією (розділ 14) |
| G6 | Користувач не чекає довше, ніж потрібно | Warm path вкладається в бюджет 6.17; cold path не блокує користувача |
| G7 | Оцінка не бреше про свою точність | Кожен аналіз має рівень впевненості й перелік попереджень (6.15) |

### 1.2 Глосарій

| Термін | Значення |
|---|---|
| **Референс** | Оригінальний вокал пісні, з яким порівнюється спів користувача |
| **Стем** | Виділена доріжка (вокал) після розділення міксу |
| **DTW** | Dynamic Time Warping — вирівнювання двох записів у часі |
| **Коридор DTW** | Обмеження області пошуку шляху (Sakoe-Chiba band) — не дає матриці зростати квадратично |
| **Цент** | 1/100 півтону; одиниця вимірювання відхилення висоти тону |
| **Onset** | Момент початку ноти/складу |
| **VAD** | Voice Activity Detection — маска "тут є голос / тут тиша" |
| **Melody extraction** | Витягування F0 вокальної партії безпосередньо з поліфонічного міксу, без повного розділення на стеми |
| **Стадія (stage)** | Один крок пайплайну з чітким контрактом входу/виходу |
| **Аналіз (analysis)** | Одне завдання: запис користувача + пісня → звіт |
| **Cold path** | Підготовка пісні (розділення + транскрипція + pitch референсу). Один раз на пісню, асинхронно, у фоні |
| **Warm path** | Власне аналіз запису користувача. Виконується щоразу, користувач чекає на результат |
| **Режим (mode)** | `clean` або `mixed` — чи присутній музичний супровід у записі користувача |
| **Зсув тональності** | Різниця в півтонах між ключем, у якому співав користувач, і ключем референсу |

## 2. Межі проекту

### 2.1 У межах (MVP)

- Реєстрація/вхід: email + пароль, Google OAuth.
- Джерело пісні: завантаження файлу **або** посилання на YouTube.
- Запис голосу у браузері (MediaRecorder) або завантаження готового файлу.
- **Два режими аналізу**: `clean` (акапельно) і `mixed` (під супровід).
- Асинхронна підготовка референсу з показом статусу.
- Черга завдань із показом позиції ("Ви номер 3 у черзі").
- Повний ML-аналіз за 6 аспектами + агрегований бал (у `mixed` — 4 аспекти).
- Нормалізація тональності (спів в іншому ключі не карається як фальш).
- Piano-roll візуалізація, текстовий звіт, бали по категоріях, рівень впевненості.
- Історія аналізів і графік прогресу з розрізненням режимів.
- Адаптивний UI (десктоп + мобільний).

### 2.2 Поза межами (не робимо в MVP)

- Аналіз у реальному часі під час співу.
- Мобільні нативні застосунки.
- Соціальні функції (шеринг, лідерборди, коментарі).
- Платежі/підписки.
- **Оцінка тембру й дихання в режимі `mixed`** — фізично недостовірна (6.14).
- Розділення супроводу на окремі інструменти (потрібен лише вокал / не-вокал).
- Оцінка гри на інструменті — аналізується виключно голос.
- Плаваючий (змінний у часі) зсув тональності — підтримується лише один
  глобальний зсув на запис (6.8).
- Горизонтальне масштабування на кілька VPS.
- Адмін-панель (керування — через SQL/CLI).
- GPU-інференс. Усі бюджети 6.17 задані для CPU. GPU-шлях не забороняється
  архітектурно, але не входить в MVP і не є умовою приймання.

### 2.3 Режими аналізу замість жорсткого припущення

Версія 1.0 містила припущення "користувач співає акапельно, в навушниках, без
фонової музики" і виносила розділення вокалу запису користувача поза межі
проекту. Практика показала, що частина користувачів співає під власний
інструмент або мінус, і для них аналіз просто ламався.

Версія 2.0 замінює припущення на **явний вибір користувача**:

| Режим | Що це | Аспекти | Точність |
|---|---|---|---|
| `clean` (рекомендований, за замовчуванням) | Акапельний спів у навушниках | усі 6 | висока |
| `mixed` | Спів під будь-який супровід | 4 з 6 (без тембру й дихання) | знижена, позначена в звіті |

**Ключове обмеження, яке зберігається:** повне розділення на стеми (Demucs) для
запису користувача **не виконується на гарячому шляху**. Причина суто
економічна: референс кешується назавжди й платиться один раз на пісню, а запис
користувача унікальний завжди — кешувати нічого. Додати Demucs у warm path
означає зруйнувати єдину оптимізацію, яка робить проект життєздатним на 4 vCPU.

Замість цього в `mixed` використовується **melody extraction** — витягування F0
вокалу безпосередньо з міксу (6.6, стадія A4). Це на порядок дешевше за
розділення й достатнє для двох аспектів, які в цьому режимі й оцінюються
(pitch і rhythm — разом 80% ваги в профілі `mixed`).

UI зобов'язаний:
- пояснити різницю між режимами **до** запису, простою мовою;
- рекомендувати `clean` і показати, що саме користувач втрачає в `mixed`;
- показати в звіті, який режим фактично застосовано і чому оцінки могли поїхати.

## 5. Архітектура і стек

### 5.1 Обґрунтування вибору

| Рішення | Чому |
|---|---|
| **Go для API** | Один статичний бінарник → легкий образ, дешева конкурентність (горутини) для WebSocket-статусів і черг, низьке споживання пам'яті під навантаженням. |
| **Python для ML** | Уся екосистема аудіо/ML (`librosa`, `Demucs`, `faster-whisper`, `torchcrepe`, `pyworld`, `dtw`) існує тільки тут. |
| **Python **не** переписується на Rust/C** | У пайплайні 90–95% wall-time виконується всередині нативних ядер: ATen/PyTorch, CTranslate2, FFmpeg, numba-код `librosa`, C++ `pyworld`. Python — це кількасот рядків оркестрації. Переписування обгортки дає ~0 виграшу, але коштує другого тулчейну в Docker-образі, другої мови в CI і прямо конфліктує з NFR-14 і ризиком "бус-фактор = 1". Виграш дають заміна раннтаймів (п. нижче), алгоритмічні обмеження (6.7) і кешування (6.13). Зафіксовано в ADR-0015. |
| **`faster-whisper` замість `openai-whisper`** | Той самий Whisper, але раннтайм CTranslate2 з int8-квантизацією: істотно швидше на CPU і менше RAM при тій же моделі. Заміна раннтайму, а не моделі — якість транскрипції зіставна. |
| **`pyworld` (DIO + StoneMask) як дефолтний pitch-рушій** | Нативний C++, працює швидше за реальний час; для монофонічного співу дає точність у центах, достатню для порівняння з референсом. CREPE лишається опційним режимом підвищеної точності (`PITCH_ENGINE=crepe`), pYIN — фолбеком. |
| **Melody extraction замість Demucs для режиму `mixed`** | Розділення на стеми для запису користувача некешоване й коштує найдорожчої стадії щоразу. Витягування F0 вокалу прямо з міксу на порядок дешевше й достатнє для аспектів, які в `mixed` взагалі оцінюються. ADR-0018. |
| **React (не Angular)** | Готові бібліотеки під аудіо (`wavesurfer.js`), легший поріг входу для соло-розробника, простіша адаптивна верстка через Tailwind. |
| **PostgreSQL** | Реляційні зв'язки user → analysis → scores + JSONB для гнучких структур без зоопарку таблиць. Щільні числові криві зберігаються як `bytea` float32, а не JSONB (7.3). |
| **Redis** | Дві черги завдань, rate limiting, кеш сесій — усе одним контейнером. |
| **Caddy (не Nginx+Certbot)** | Авто-HTTPS без ручного renewal, коротший конфіг, одразу віддає статику React — на один контейнер менше. |
| **Локальний Docker volume (не S3/Spaces)** | Аудіо користувача живе 5 хвилин, CDN не потрібен. Ваги моделей і вокальні стеми референсів — в окремих іменованих volume. |

### 5.3 Сервіси Docker Compose

| Сервіс | Образ/збірка | Порти назовні | Примітка |
|---|---|---|---|
| `caddy` | `caddy:2-alpine` | 80, 443 | єдиний сервіс із публічними портами |
| `go-api` | multi-stage build (distroless) | — | лише внутрішня мережа |
| `python-worker` | multi-stage build (slim) | — | без публічних портів, ваги моделей у volume, ліміти CPU/RAM обов'язкові |
| `postgres` | `postgres:16-alpine` | — | **порт не публікується на хост** |
| `redis` | `redis:7-alpine` | — | **порт не публікується**, `requirepass` |
| `backup` | `postgres:16-alpine` + cron | — | нічний `pg_dump` |

Правила compose:
- Образи фіксуються тегом і digest (`image: postgres:16-alpine@sha256:...`), `latest` заборонено.
- Усі сервіси: `restart: unless-stopped`, `user:` non-root, `cap_drop: [ALL]`,
  `security_opt: [no-new-privileges:true]`, `read_only: true` де можливо (+ `tmpfs` для /tmp).
- Healthcheck для кожного сервісу; `depends_on: condition: service_healthy`.
- `python-worker`: `deploy.resources.limits` на CPU і RAM (щоб OOM не вбив Postgres),
  `stop_grace_period: 180s` (довша за v1.0 — стадія розділення не переривається миттєво),
  змінні `OMP_NUM_THREADS` та інші за 6.11 задаються тут, а не всередині коду.
- Ваги моделей завантажуються один раз окремим `init`-кроком у volume, не при кожному старті.

## 6. ML-пайплайн

### 6.1 Два режими аналізу

Режим задається користувачем у `POST /analyses` і визначає, які стадії
виконуються та які аспекти оцінюються.

| | `clean` | `mixed` |
|---|---|---|
| Що записує користувач | голос без супроводу, у навушниках | голос + будь-який інструмент/мінус |
| Джерело F0 користувача | pitch-рушій напряму по запису | melody extraction з міксу (A4) |
| Оцінювані аспекти | pitch, rhythm, vibrato, breath, dynamics, timbre | pitch, rhythm, vibrato, dynamics |
| Нормалізація тональності | вимкнена (опційно вмикається користувачем) | увімкнена за замовчуванням |
| Профіль ваг | `clean_v1` | `mixed_v1` |
| Базова впевненість | `high` | `medium` |
| Бюджет warm path | 90 с | 150 с |

Режим, який фактично виконався, зберігається окремо (`effective_mode`), бо
система може знизити `mixed` до `clean`, якщо супроводу насправді немає (6.16).

### 6.2 Два шляхи виконання

Головна архітектурна зміна v2.0: важкі одноразові стадії винесені з шляху,
на якому чекає користувач.

```
POST /songs ──► черга songs:prep ──► COLD PATH (P1–P4)  ──► songs.prep_status = ready
                                     Demucs, Whisper,        (кеш назавжди)
                                     pitch референсу
                                     ~10 хв, у фоні

POST /analyses ──► черга analyses:run ──► [чекає songs.prep_status = ready]
                                     ──► WARM PATH (A1–A9)
                                          ~90 с (clean) / ~150 с (mixed)
                                     ──► результат
```

Практичний наслідок: користувач додає пісню, читає пояснення режимів і
записує свої 3 хвилини — за цей час cold path уже відпрацював. Перший аналіз
відчувається майже так само швидко, як другий.

Якщо аналіз поставлено раніше, ніж пісня готова, він переходить у стан
`waiting_for_reference` і отримує WS-події про прогрес підготовки (FR-16).

### 6.3 Контракт стадії

Кожна стадія реалізує один інтерфейс (12.3):

- вхід: `PipelineContext` (шляхи до аудіо, спільний кеш фіч, попередні
  результати, конфіг, режим);
- вихід: `StageResult` (JSON-серіалізовний, пишеться в `*.stages_json`);
- властивості: **ідемпотентна**, з таймаутом, без побічних ефектів поза
  контекстом і БД;
- **обов'язково** логує старт/фініш із `job_id`, тривалістю в мілісекундах і
  піковою RSS; тривалість пишеться в `stage_durations_json` (NFR-15).

Стадія оголошує, чи є вона **обов'язковою**. Необов'язкова стадія при збої
або таймауті не валить пайплайн: вона пише причину в `warnings_json`, а
залежні від неї аспекти стають `null` (FR-41).

### 6.4 Cold path — підготовка пісні (стадії P)

Виконується один раз на пісню, асинхронно, результат кешується безстроково.

| # | Стадія | Технологія | Таймаут | Обов'язкова |
|---|---|---|---|---|
| P1 | Декодування й нормалізація референсу | `ffmpeg` (один прохід) | 60 с | так |
| P2 | Розділення вокалу | Demucs v4, `--two-stems=vocals`, `shifts=0`, `segment=7` | 600 с | так |
| P3 | Транскрипція лірики | `faster-whisper`, int8, модель `base` | 240 с | **ні** (FR-18) |
| P4 | Pitch-крива референсу + фічі вирівнювання | `pyworld` / `torchcrepe` + chroma | 120 с | так |

Результат P2 (вокальний стем) зберігається у volume `song-cache`, P3 — у
`songs.lyrics_json`, P4 — у `songs.reference_pitch` (`bytea` float32) і
`songs.align_features` (`bytea` float32).

### 6.5 Warm path — аналіз запису (стадії A)

| # | Стадія | Технологія | Таймаут | `clean` | `mixed` |
|---|---|---|---|---|---|
| A1 | Декодування й нормалізація запису | `ffmpeg` (один прохід) | 45 с | ✓ | ✓ |
| A2 | VAD-маска (голос / тиша) | Silero VAD (ONNX) | 20 с | ✓ | ✓ |
| A3 | Класифікація входу і звірка з режимом | енергія в невокальних кадрах, HPSS | 15 с | ✓ | ✓ |
| A4 | Витягування F0 вокалу з міксу | melody extraction (ONNX) | 90 с | — | ✓ |
| A5 | Pitch-крива користувача | `pyworld` / `torchcrepe` / `pyin` | 60 с | ✓ | — |
| A6 | Спільний кеш фіч (STFT/mel/chroma) | `librosa`, один прохід | 25 с | ✓ | ✓ |
| A7 | Вирівнювання: дворівневий обмежений DTW | власна реалізація на `numba` | 45 с | ✓ | ✓ |
| A8 | Нормалізація тональності | медіана зсуву по вирівняних кадрах | 5 с | опційно | ✓ |
| A9 | Аспектні стадії (паралельно): pitch, rhythm, vibrato, dynamics, timbre, breath | numpy / `librosa` над кешем A6 | 60 с на всі | 6 аспектів | 4 аспекти |
| A10 | Агрегація балів, впевненість, звіт | власна логіка | 10 с | ✓ | ✓ |

### 6.6 Деталі стадій

**P1 / A1 — декодування й нормалізація.** Один виклик `ffmpeg` замість
ланцюжка завантажень через `librosa`: декодування, конвертація в моно,
ресемплінг і нормалізація гучності (`loudnorm`, ціль −23 LUFS) виконуються за
один прохід. Це водночас санітизація контейнера (11.3).

Готуються три представлення, бо різні моделі хочуть різну частоту:

| Файл | Формат | Для чого |
|---|---|---|
| `*_44k.wav` | 44.1 kHz, стерео | вхід Demucs (тільки cold path) |
| `*_22k.wav` | 22.05 kHz, моно | `librosa`-фічі, pitch-рушії, DTW |
| 16 kHz моно | в пам'яті, з `*_22k` | Whisper, VAD, CREPE, melody extraction |

Проміжні файли живуть у `audio-tmp` і видаляються за NFR-11.

**P2 — розділення вокалу референсу.** Demucs v4 (`htdemucs`). Алгоритми pitch
плутаються, коли одночасно звучать бас, ударні й гармонії — виникають октавні
помилки, тому чистий стем потрібен. Обов'язкові параметри, зафіксовані в
конфігу: `shifts=0` (кожен додатковий shift множить час лінійно й дає приріст
якості, який тут не потрібен), `--two-stems=vocals`, `segment=7` (обмежує пікову
RAM), `jobs` = `WORKER_CPU_THREADS`. Стадія виконується в дочірньому процесі.

**P3 — транскрипція лірики.** `faster-whisper` (раннтайм CTranslate2) з
`compute_type=int8`, модель за замовчуванням `base`, мультимовна (укр/англ) →
текст із таймкодами по словах у `songs.lyrics_json`. Стадія **необов'язкова**:
лірика використовується як фолбек вирівнювання (6.7) і для майбутніх функцій,
але аналіз без неї працює.

**P4 — pitch-крива референсу і фічі вирівнювання.** Той самий рушій, що й для
користувача (детермінізм порівняння). Рахується один раз, кладеться в кеш.
Разом із нею рахуються chroma-фічі з грубим кроком для DTW (6.7).

**A2 — VAD.** Silero VAD в ONNX-раннтаймі: дешева маска "голос / не голос".
Ця маска — головний важіль економії: у типовому треку 30–50% часу без вокалу, і
всі per-frame стадії працюють **тільки по вокальних кадрах**. Маска також
використовується стадією A3 і аспектом дихання.

**A3 — класифікація входу.** Див. 6.16.

**A4 — melody extraction (тільки `mixed`).** Модель, що витягує F0 вокальної
партії безпосередньо з поліфонічного міксу, в ONNX-раннтаймі. Демукс на записі
користувача **не запускається** (2.3). Конфіг `MIXED_MODE_ENGINE`:
- `melody` (за замовчуванням) — витягування F0 з міксу;
- `separate` (за прапорцем, вимкнено) — легкий квантизований сепаратор + звичайний
  pitch-рушій. Дозволено лише для офлайн-експериментів і порівняння якості, не
  для продакшн-навантаження.

> **Спайк на етапі M3, з go/no-go критерієм.** Перед впровадженням режиму
> `mixed` виконується перевірка на синтетичних фікстурах (відомий F0 вокалу +
> накладений супровід при SNR 0 дБ і −6 дБ). Критерій прийняття: медіанна
> помилка F0 < 50 центів на вокальних кадрах. Якщо критерій не досягнуто —
> режим `mixed` виходить із урізаним набором аспектів (лише rhythm) або
> переноситься за межі MVP окремим ADR. Обіцяти якість наперед ТЗ не має права.

**A5 — pitch-крива користувача (тільки `clean`).** Рушій за конфігом
`PITCH_ENGINE`:

| Значення | Реалізація | Коли |
|---|---|---|
| `pyworld` (за замовчуванням) | DIO + StoneMask, нативний C++ | дефолт: швидко, точності в центах достатньо |
| `crepe` | `torchcrepe`, `capacity` з конфігу | коли є запас CPU і потрібна максимальна точність |
| `pyin` | `librosa.pyin` | фолбек |

Обов'язкова постобробка: медіанний фільтр + корекція октавних стрибків
(стрибок рівно на ±12 півтонів між сусідніми вокальними кадрами трактується як
помилка детектора, а не як спів). Поріг і вікно — іменовані константи в конфігу.

**A6 — спільний кеш фіч.** Один STFT і один mel-спектрограма на аудіо,
покладені в `PipelineContext`. Аспектні стадії (rhythm, dynamics, timbre,
breath) **зобов'язані** брати їх звідти. Повторний виклик `librosa`, який
рахує спектр наново, — блокер на рев'ю (12.6).

**A9 — аспектні стадії.**

1. **Pitch** — порівняння нота-в-ноту з референсом після вирівнювання (A7) і
   зсуву тональності (A8), відхилення в центах.
2. **Rhythm** — порівняння onset-таймінгів після вирівнювання: наскільки рано
   чи пізно користувач вступає. Onset-огинаюча береться з кешу A6.
3. **Vibrato** — аналіз частотної модуляції pitch-кривої (частота і глибина
   коливань) на витриманих нотах.
4. **Dynamics** — RMS-огинаюча з кешу A6: порівняння форми динаміки (де мало
   бути крещендо, а вийшло рівно). У `mixed` рахується, але з позначкою, що на
   огинаючу впливає супровід.
5. **Timbre** — порівняння MFCC-профілів. Грубий індикатор "схожості
   звучання", **без претензії на точну діагностику вокальної техніки** — це
   формулювання обов'язкове й у тексті звіту. **У `mixed` не рахується**:
   MFCC міксу описує ансамбль, а не голос.
6. **Breath** — детекція пауз (ділянки тиші/низької енергії за маскою A2) і
   порівняння місць вдихів із референсом. **У `mixed` не рахується**: у паузах
   між фразами звучить інструмент, і сама ознака зникає.

**A10 — агрегація.** Зважена сума доступних під-оцінок за профілем режиму
(6.14) + розрахунок впевненості (6.15) + генерація тексту звіту.

### 6.7 Вирівнювання: дворівневий обмежений DTW

Найдорожча помилка v1.0 була тут. Наївний DTW по pitch-кривій із кроком 10 мс
для двох 3-хвилинних записів — це матриця приблизно 18 000 × 18 000 ≈ 3·10⁸
клітинок: кілька гігабайт пам'яті й хвилини часу. Тому:

**Рівень 1 — грубе вирівнювання.**
- Фічі: chroma (12 вимірів) з кроком `DTW_COARSE_HOP_MS` (за замовчуванням 50 мс).
- Довжина послідовностей падає в ~5 разів проти 10 мс.
- Обмеження коридору: Sakoe-Chiba шириною `DTW_BAND_SECONDS` (за замовчуванням
  ±10 с). Зберігається **тільки смуга**, не повна матриця (NFR-16).
- Реалізація динамічного програмування — `numba`-jit. Пряма реалізація
  вкладеними Python-циклами заборонена (NFR-17).

**Рівень 2 — уточнення.**
- Тільки на вокальних кадрах (маска A2).
- Крок `DTW_FINE_HOP_MS` (10 мс), вікно пошуку ±`DTW_REFINE_WINDOW_MS`
  (за замовчуванням ±200 мс) навколо шляху з рівня 1.

**Захисні запобіжники.**
- Перед стартом рахується оцінка розміру задачі. Якщо кількість клітинок у
  смузі перевищує `DTW_MAX_CELLS` — стадія падає з `ALIGNMENT_TOO_LARGE`,
  а не з'їдає пам'ять воркера.
- `alignment_cost` (нормалізована вартість шляху) зберігається в БД і входить
  у розрахунок впевненості (6.15).
- Якщо вартість вища за `ALIGNMENT_COST_MAX`, є два фолбеки по черзі:
  вирівнювання по словах із лірики Whisper (якщо `lyrics_available`), потім
  чесна помилка `ALIGNMENT_FAILED`.

Виграш проти реалізації v1.0 — на два порядки, без жодного рядка нативного коду.

### 6.8 Нормалізація тональності

Проблема, якої не було в v1.0: користувач із гітарою майже завжди співає в
**іншому ключі** — капо, транспоновані акорди, просто зручніший діапазон. DTW
компенсує темп, але не висоту. Без нормалізації ідеальний спів на 2 півтони
нижче отримує pitch-бал близько нуля.

**Алгоритм.**
1. По вирівняних вокальних кадрах рахується різниця `user_semitones −
   reference_semitones`.
2. Оцінка зсуву — **медіана** цієї різниці (стійка до окремих фальшивих нот).
3. Рахується розкид (IQR) різниці — міра того, наскільки зсув справді
   постійний.

**Коли зсув застосовується.** Тільки якщо виконано **всі** умови:
- режим `mixed`, або користувач явно ввімкнув `allow_transposition` (FR-31);
- `|медіана| ≥ KEY_SHIFT_MIN_SEMITONES` (за замовчуванням 0.6 півтону);
- `IQR ≤ KEY_SHIFT_MAX_IQR` (за замовчуванням 0.5 півтону) — зсув стабільний;
- `|медіана| ≤ MAX_KEY_SHIFT_SEMITONES` (за замовчуванням 7).

**Чому такі жорсткі умови.** Це найнебезпечніша функція в пайплайні: без
обмежень вона пробачає реальну фальш. Користувач, який стабільно співає на
півтону нижче, — це не транспозиція, а помилка інтонації, і вона має каратися.
Саме тому:
- в `clean` нормалізація **вимкнена за замовчуванням** (людина співає під
  оригінал у навушниках — транспонувати нема куди);
- мінімальний поріг 0.6 півтону відсікає "розмазану" інтонацію;
- вимога стабільності (IQR) відрізняє транспонування від плавання по тону.

**Що бачить користувач.** Зсув ніколи не приховується: звіт повідомляє
"ви співали на 2 півтони нижче за оригінал — оцінка це врахувала"
(`key_shift_semitones` у відповіді API, FR-46). Якщо медіана перевищує
`MAX_KEY_SHIFT_SEMITONES`, зсув не застосовується, а в `warnings_json`
додається `KEY_SHIFT_OUT_OF_RANGE` — найімовірніше, це не транспозиція, а
збите вирівнювання.

Плаваючий у часі зсув (модуляція посеред пісні) у MVP не підтримується (2.2).

### 6.9 Спільний кеш фіч

`PipelineContext` містить лениво обчислювані й закешовані представлення:
STFT, mel-спектрограма, chroma, RMS-огинаюча, onset-огинаюча, MFCC, VAD-маска —
окремо для запису користувача й для референсу.

Правило: **кожне представлення рахується не більше одного разу на аудіо за
весь пайплайн.** Це не мікрооптимізація: у v1.0 п'ять аспектних стадій
незалежно викликали `librosa` і кожна рахувала спектр наново.

### 6.10 Паралельне виконання аспектних стадій

Стадії A9 залежать лише від виходів A6–A8 і **не залежать одна від одної**,
тому виконуються паралельно (`PIPELINE_PARALLEL_ASPECTS=true`).

- Пул: `min(WORKER_CPU_THREADS, кількість активних аспектів)`.
- **Обов'язково:** на час паралельної секції кількість потоків BLAS на кожну
  задачу зводиться до 1. Інакше 4 стадії × 4 потоки = 16 потоків на 4 vCPU,
  і паралелізм дає уповільнення замість прискорення. Це найтиповіша пастка
  в цьому місці, тому винесена в явну вимогу.
- Збій однієї аспектної стадії не валить решту: аспект стає `null` із
  причиною, інші рахуються (6.3).

Послідовний режим (`PIPELINE_PARALLEL_ASPECTS=false`) зберігається для
відтворюваності в тестах.

### 6.11 Конфігурація CPU і потоків

Покладатися на дефолти бібліотек заборонено (NFR-18). Воркер на старті:

- читає `WORKER_CPU_THREADS` (за замовчуванням — кількість доступних vCPU з
  урахуванням cgroup-ліміту контейнера, а не кількості ядер хоста);
- виставляє `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS`,
  `NUMEXPR_NUM_THREADS` **до** імпорту numpy/torch;
- викликає `torch.set_num_threads()` і `torch.set_num_interop_threads()`;
- логує підсумкову конфігурацію одним рядком на старті — щоб при розборі
  повільного аналізу це було видно одразу.

### 6.12 Керування пам'яттю

На 8 ГБ RAM Demucs і Whisper **не можуть жити в пам'яті одночасно**. Вимоги:

- Кожна важка модель завантажується ліниво, через єдиний `ModelRegistry` з
  явним `release()` після стадії (`del model; gc.collect()`).
- Стадії P2 і P3 виконуються в окремому дочірньому процесі — гарантоване
  повернення пам'яті ОС після завершення.
- Ваги моделей монтуються з окремого volume і не завантажуються при кожному
  старті контейнера.
- Версії ваг фіксуються в конфігу і пишуться в `analyses.model_versions` та
  `songs.model_versions`.
- Один ML-слот на воркер (10.2): підготовка й аналіз ніколи не виконуються
  одночасно, тому пікова RAM визначається найважчою окремою стадією.

### 6.13 Кешування референсу

Ключ кешу — `sha256` нормалізованого аудіо (для завантаження файлом) або
`youtube_video_id`. Якщо `songs.prep_status = ready`, увесь cold path
пропускається. Це головна оптимізація проекту: другий і кожен наступний аналіз
тієї ж пісні коштує в рази дешевше за перший.

Вимоги до реалізації:
- Хеш рахується **після** нормалізації P1, а не по сирому файлу: той самий трек
  у mp3 і у flac має давати один запис `songs`.
- Промах кешу логується з причиною — щоб мовчазна деградація (кеш є, але не
  спрацьовує через різний хеш) не з'їдала ресурси непомітно.
- Метрика `cache_hit_ratio` по підготовках виводиться в лічильники (17.3).

### 6.14 Доступність аспектів і профілі ваг

| Аспект | `clean` | `mixed` | Чому |
|---|---|---|---|
| pitch | 0.35 | 0.50 | основний і найстійкіший аспект |
| rhythm | 0.20 | 0.30 | onset-и переживають наявність супроводу |
| breath | 0.15 | **null** | у паузах звучить інструмент — ознака зникає |
| dynamics | 0.10 | 0.10 | рахується, але на огинаючу впливає супровід |
| vibrato | 0.10 | 0.10 | рахується по F0, стійкий за умови коректної A4 |
| timbre | 0.10 | **null** | MFCC міксу описує ансамбль, а не голос |

Профілі ваг (`clean_v1`, `mixed_v1`) задаються конфігом, а не константами в
коді, і зберігаються разом з аналізом (`analyses.scoring_version`,
`analyses.weights_profile`), щоб старі результати залишались відтворюваними
після зміни формули.

**Правила, обов'язкові до виконання:**
- Недоступний аспект — це `null` із машиночитною причиною, **ніколи не `0`**
  (FR-41). Нуль означає "співав погано", `null` означає "не міряли".
- Ваги в межах профілю нормуються до 1.0 по доступних аспектах.
- `overall_score`, порахований за різними профілями, **не є прямо
  порівнюваним**. Графік прогресу (FR-49) зобов'язаний це показувати.

### 6.15 Модель впевненості

Кожен аналіз має загальний рівень впевненості й рівень по кожному аспекту:
`high` / `medium` / `low`. Це не косметика — без нього продукт видає точні на
вигляд числа там, де вимірювання ненадійне (G7, ризик "оцінки виглядають
несправедливими").

Впевненість знижують:

| Фактор | Джерело | Ефект |
|---|---|---|
| режим `mixed` | вибір користувача | стеля впевненості — `medium` |
| виявлено супровід у режимі `clean` | A3 | −1 рівень, попередження `ACCOMPANIMENT_IN_CLEAN_MODE` |
| низька частка вокальних кадрів (`voiced_ratio`) | A2 | −1 рівень, попередження `LITTLE_VOICE_DETECTED` |
| висока вартість вирівнювання (`alignment_cost`) | A7 | −1 рівень, попередження `WEAK_ALIGNMENT` |
| зсув тональності поза діапазоном | A8 | −1 рівень, попередження `KEY_SHIFT_OUT_OF_RANGE` |
| лірика недоступна | P3 | без ефекту на бали, тільки позначка |
| низька впевненість melody extraction | A4 | −1 рівень для pitch і vibrato |

Пороги — іменовані константи в конфігу. Впевненість і перелік попереджень
повертаються API і показуються користувачу людською мовою (FR-47).

### 6.16 Класифікація входу і звірка з режимом

Стадія A3 визначає, чи є в записі супровід. Основна ознака — **енергія в
невокальних кадрах**: у справжньому акапельному записі там майже тиша, а якщо
звучить інструмент, енергія зберігається й у паузах між фразами.

```
accompaniment_level = median(RMS невокальних кадрів) / median(RMS вокальних кадрів)
```

Додаткові ознаки: частка перкусивної компоненти (HPSS) і енергія в смузі нижче
120 Гц (бас, бочка) — вокал туди майже не заходить.

| Заявлений режим | `accompaniment_level` | Дія |
|---|---|---|
| `clean` | < порогу | норма, виконується clean-шлях |
| `clean` | ≥ порогу | **аналіз виконується**, додається попередження, впевненість −1, UI пропонує перезапуск у `mixed` (FR-30) |
| `mixed` | ≥ порогу | норма, виконується mixed-шлях |
| `mixed` | < порогу | **авто-даунгрейд до `clean`** (FR-29): дешевше й точніше; `effective_mode = clean`, у звіті — позначка |

Поріг `ACCOMPANIMENT_DETECT_THRESHOLD` (за замовчуванням 0.15) — конфіг, не
константа в коді. Виявлення супроводу **ніколи не є помилкою** й ніколи не
блокує результат.

Дублююча перевірка виконується у браузері перед завантаженням (Web Audio API,
та сама формула по енергії в паузах): користувач бачить "ми чуємо музику,
увімкнути режим `mixed`?" за секунду, а не через 8 хвилин очікування в черзі.
Серверна перевірка при цьому залишається джерелом істини — браузерна лише
економить час користувача.

### 6.17 Бюджет продуктивності

Бюджети задані для 4 vCPU, референсна пісня 3 хв (cold path — 6 хв), без
черги. Це **вимога, що перевіряється тестом** (NFR-19), а не побажання.

**Cold path (асинхронно, один раз на пісню):**

| Стадія | Бюджет |
|---|---|
| P1 декодування й нормалізація | 20 с |
| P2 Demucs (`shifts=0`, `segment=7`) | 420 с |
| P3 `faster-whisper base` int8 | 90 с |
| P4 pitch референсу + фічі | 40 с |
| **Разом** | **≤ 570 с** (NFR-01a: 600 с) |

**Warm path, режим `clean` (користувач чекає):**

| Стадія | Бюджет |
|---|---|
| A1 декодування й нормалізація | 12 с |
| A2 VAD | 5 с |
| A3 класифікація входу | 4 с |
| A5 pitch користувача (по вокальних кадрах) | 18 с |
| A6 спільний кеш фіч | 12 с |
| A7 дворівневий DTW | 15 с |
| A8 нормалізація тональності | 2 с |
| A9 аспектні стадії (паралельно) | 15 с |
| A10 агрегація і звіт | 3 с |
| **Разом** | **≤ 86 с** (NFR-01b: 90 с) |

**Warm path, режим `mixed`:** те саме без A5, плюс A4 melody extraction
(бюджет 60 с) → **≤ 128 с** (NFR-01c: 150 с).

**Порядок дій при невкладанні в бюджет** (саме в такій послідовності, згори вниз):

1. Перевірити, чи спрацьовує кеш референсу (6.13) — промах кешу дає найбільшу
   і найчастішу деградацію.
2. Перевірити конфігурацію потоків (6.11) — і недовикористання, і
   перепідписка виглядають однаково "повільно".
3. Подивитися `stage_durations_json` і оптимізувати **конкретну** найдорожчу
   стадію. Оптимізація без цих даних заборонена.
4. Знизити параметри моделей: `WHISPER_MODEL=tiny`, `PITCH_ENGINE=pyworld`,
   грубіший `DTW_COARSE_HOP_MS`.
5. Обмежити ділянку аналізу (`ANALYSIS_MAX_SECONDS`, наприклад тільки приспів).
6. Збільшити ресурси VPS.

Пункт "переписати частину на Rust/C" у цьому списку відсутній свідомо: див.
5.1 і ADR-0015. Він розглядається лише як наслідок кроку 3, якщо профіль
покаже, що вузьке місце — **власний** Python-код, а не бібліотечний, і що
`numba` його не закриває.

### 6.18 Обробка помилок, попередження, повтори

**Помилки** (аналіз падає, `status = failed`, машиночитний `error_code`):

| Код | Значення |
|---|---|
| `REFERENCE_TOO_QUIET` | референс не містить придатного вокалу |
| `REFERENCE_PREP_FAILED` | cold path пісні впав (FR-17) |
| `NO_VOICE_DETECTED` | у записі користувача не знайдено голосу |
| `ALIGNMENT_FAILED` | вирівнювання не вдалося навіть після фолбеків |
| `ALIGNMENT_TOO_LARGE` | задача вирівнювання перевищує `DTW_MAX_CELLS` |
| `MELODY_EXTRACTION_FAILED` | режим `mixed`, F0 витягти не вдалося |
| `TIMEOUT` | стадія перевищила таймаут |
| `INTERNAL` | усе інше |

**Попередження** (аналіз успішний, коди в `warnings_json`, впливають лише на
впевненість): `ACCOMPANIMENT_IN_CLEAN_MODE`, `MODE_DOWNGRADED_TO_CLEAN`,
`LITTLE_VOICE_DETECTED`, `WEAK_ALIGNMENT`, `KEY_SHIFT_OUT_OF_RANGE`,
`LYRICS_UNAVAILABLE`, `ASPECT_UNAVAILABLE`.

**Повтори.** Транзієнтні помилки (таймаут, тимчасова недоступність БД) — до 2
повторів з експоненційною затримкою; логічні помилки не повторюються. Повтор
починається з першої незавершеної стадії, а не з нуля. Cold path і warm path
перезапускаються незалежно.

### 6.19 Формат результату

- **Piano-roll**: pitch-крива користувача поверх референсної (після
  вирівнювання і зсуву тональності), кольором позначені фальшиві ноти.
- **Текстовий звіт** по кожному *доступному* аспекту з конкретними порадами.
  Недоступні аспекти показуються окремим блоком із поясненням причини, а не
  ховаються.
- **Бали/відсотки** по кожній доступній категорії + загальний.
- **Метадані чесності**: режим, фактичний режим, зсув тональності, рівень
  впевненості, перелік попереджень.

### 6.20 Заборонені реалізації (перф-антипатерни)

Кожен пункт — блокер на рев'ю, не рекомендація:

- Повний DTW без обмеження коридору (NFR-16).
- Щільні per-frame цикли на чистому Python (NFR-17).
- Повторний розрахунок STFT/mel/chroma там, де є кеш A6 (6.9).
- Виклик pitch-рушія по всьому запису замість вокальних кадрів (6.6, A2).
- Запуск Demucs на записі користувача в warm path (2.3).
- Покладання на дефолтну кількість потоків BLAS/torch (NFR-18).
- Зберігання щільних числових кривих як JSONB замість `bytea` float32 (7.3).
- Завантаження ваг моделі всередині циклу або на кожному аналізі замість
  `ModelRegistry` (6.12).
- Оптимізація "на око", без даних `stage_durations_json` (6.17).

### 7.1 Індекси та обмеження

- `analyses(user_id, created_at DESC)` — історія з пагінацією.
- `analyses(status)` частковий `WHERE status IN ('queued','waiting_for_reference','processing')` — моніторинг черги.
- `analyses(song_id) WHERE status = 'waiting_for_reference'` — швидко знайти
  аналізи, які треба розбудити після готовності пісні.
- `songs(content_hash)` unique — дедуплікація.
- `songs(prep_status) WHERE prep_status IN ('pending','processing')` — моніторинг cold path.
- `progress_snapshots(user_id, mode, created_at)` — графік прогресу з розрізненням режимів.
- `users(email) WHERE deleted_at IS NULL` unique.
- Усі FK — `ON DELETE CASCADE` від `users`; видалення акаунта прибирає все.
- `CHECK` на всі `*_score`: `score IS NULL OR (0 <= score <= 100)`.
  **Важливо:** обмеження має допускати `NULL` — у режимі `mixed` частина
  аспектів не рахується (FR-41).
- `CHECK (mode = 'mixed' OR breath_score IS NOT NULL OR status <> 'done')` —
  захист від тихої втрати аспекта в `clean`.
- Часові поля — `timestamptz`, зберігаються в UTC.

### 7.2 Життєвий цикл даних

| Дані | Термін зберігання |
|---|---|
| Завантажене аудіо користувача | ≤ 5 хв після завершення обробки |
| Нормалізоване аудіо референсу | ≤ 5 хв після завершення cold path |
| Вокальний стем референсу | кешується, поки існує `songs`-запис |
| Pitch-крива й фічі референсу | кешуються, поки існує `songs`-запис |
| Результати аналізу (бали, криві, звіт) | безстроково, до видалення акаунта |
| Неверифікований акаунт | 24 год |
| Дамп БД | 14 днів локально |

### 7.3 Зберігання числових кривих

Pitch-крива 3-хвилинного запису з кроком 10 мс — це ~18 000 значень. У JSONB
це сотні кілобайт тексту на кожен аналіз, які до того ж треба парсити.

Правило:
- **Щільні криві** (`reference_pitch`, `align_features`, `user_pitch`) —
  `bytea`, масив `float32` little-endian, метадані (крок, частота, довжина,
  рушій) поруч у JSONB. Приблизно вчетверо компактніше й без парсингу тексту.
- **Дані для UI** (`pitch_curve_json`) — прорідена до ~2 000 точок крива,
  придатна для рендера piano-roll без додаткової обробки на фронті.
- JSONB залишається для того, для чого він потрібен: лірика, бали,
  попередження, тривалості стадій, проміжні результати.

## 8. API-контракт

`api/openapi.yaml` (OpenAPI 3.1) — **єдине джерело істини**. TypeScript-клієнт
для фронтенду генерується з нього; ручне дублювання типів заборонено.

### 8.1 Загальні правила

- Базовий префікс `/api/v1`. Ламкі зміни → `/api/v2`, стара версія живе до
  міграції фронтенду.
- Формат помилок — RFC 9457 `application/problem+json`:
  ```json
  { "type": "about:blank", "title": "Too Many Requests",
    "status": 429, "detail": "Queue is full, try again in a few minutes",
    "code": "QUEUE_FULL", "request_id": "..." }
  ```
- `code` — машиночитний, стабільний; `detail` — для людини, локалізується на фронті за `code`.
- Пагінація — курсорна (`?cursor=&limit=`), не offset.
- Кожна відповідь містить `X-Request-Id`.

### 8.3 `POST /analyses` — запит

```json
{
  "song_id": "uuid",
  "recording_id": "uuid",
  "mode": "clean",
  "allow_transposition": false
}
```

- `mode` — `clean` (за замовчуванням) або `mixed` (FR-27).
- `allow_transposition` — за замовчуванням `false` для `clean` і `true` для
  `mixed` (FR-31, 6.8).
- Якщо пісня ще не готова, відповідь — `202` зі `status: "waiting_for_reference"`,

### 8.4 `GET /analyses/{id}` — відповідь (успішний `mixed`)

```json
{
  "id": "uuid",
  "status": "done",
  "mode": "mixed",
  "effective_mode": "mixed",
  "scores": {
    "pitch": 78, "rhythm": 71, "vibrato": 64, "dynamics": 69,
    "breath": null, "timbre": null,
    "overall": 73
  },
  "unavailable_aspects": {
    "breath": "NOT_MEASURABLE_WITH_ACCOMPANIMENT",
    "timbre": "NOT_MEASURABLE_WITH_ACCOMPANIMENT"
  },
  "confidence": "medium",
  "aspect_confidence": { "pitch": "medium", "rhythm": "medium",
                         "vibrato": "low", "dynamics": "low" },
  "key_shift_semitones": -2,
  "warnings": ["KEY_SHIFT_APPLIED"],
  "weights_profile": "mixed_v1",
  "scoring_version": "2.0",
  "feedback_text": "...",
  "pitch_curve": { "hop_ms": 90, "user": [...], "reference": [...] }
}
```

Контрактні правила:
- Недоступний аспект — `null` + запис в `unavailable_aspects`, ніколи `0` (FR-41).
- `overall` завжди присутній і завжди супроводжується `weights_profile`.
- Клієнт **не має права** порівнювати `overall` між різними `weights_profile`
  без явної позначки для користувача (FR-49).

### 8.5 WebSocket

`GET /api/v1/ws/analyses/{id}` — автентифікація тим самим access-токеном
(перше повідомлення після конекту, не query-параметром: токени не потрапляють
у логи проксі).

Події (JSON, поле `type`):

| type | payload |
|---|---|
| `queued` | `position` |
| `waiting_for_reference` | `song_id`, `prep_stage`, `prep_progress` |
| `stage` | `name`, `index`, `total` |
| `warning` | `code` — попередження, отримане під час обробки (6.18) |
| `done` | `analysis_id` |
| `failed` | `error_code`, `message` |

Пінг кожні 30 с, автоперепідключення на фронті з backoff. WebSocket — лише
транспорт статусів; фінальний результат завжди дочитується через REST
(fallback на polling, якщо WS недоступний).

## 9. Авторизація і сесії

- Реєстрація: email + пароль **або** Google OAuth.
- Email-реєстрація → 6-значний код на пошту → `verification_expires_at` (24 год).
- Фонова задача в Go API (тікер раз на годину) видаляє акаунти з
  `email_verified = false` і простроченим `verification_expires_at`.
- Сесії: короткоживучий JWT access-token (15 хв) + refresh-token у httpOnly
  cookie, ротація refresh-токена в Redis (можливість миттєвого відкликання).
- Паролі: `argon2id` (fallback `bcrypt`), ніколи не логуються, ніколи в
  звичайному тексті.

### 9.1 Додаткові вимоги

- **Reuse detection**: повторне використання вже відкликаного refresh-токена
  трактується як компрометація → відкликається вся родина токенів користувача.
- Cookie: `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`.
- Код верифікації зберігається лише як хеш; порівняння — константа за часом;
  ≤ 5 спроб, далі код інвалідується.
- Захист від перебору пароля: експоненційна затримка по парі (email, IP),
  блокування на 15 хв після 10 невдач.
- Відповіді на `/auth/login` і `/auth/register` не розкривають, чи існує email
  (однакові тексти й час відповіді).
- Google OAuth: перевірка `state` (CSRF), PKCE, прив'язка `google_id` до
  наявного акаунта лише при збігу верифікованого email.
- Політика пароля: мінімум 10 символів, перевірка за списком найпоширеніших
  (без вимог до "спецсимволів" — вони погіршують реальну стійкість).

## 10. Черги завдань

### 10.1 Дві черги

| Стрім | Що обробляє | Джерело | Пріоритет |
|---|---|---|---|
| `analyses:run` | warm path (A1–A10) | `POST /analyses` | високий |
| `songs:prep` | cold path (P1–P4) | `POST /songs`, `POST /songs/{id}/prepare` | низький, з підвищенням |

- Redis Streams (`XADD`), окрема consumer group на кожен стрім, `XACK` після
  завершення.
- Go API при постановці аналізу рахує `XLEN` → повертає користувачу оцінку
  позиції одразу, далі оновлює через WebSocket.
- Захист від переповнення: черга довша за поріг (20 на кожен стрім) → нові
  завдання отримують `429 Too Many Requests` з чіткою відповіддю.
- Rate limiting на рівні користувача: sliding-window лічильник у Redis
  (не більше 10 аналізів на годину на акаунт).

### 10.2 Один ML-слот і планування

Воркер читає обидва стріми, але **виконує одночасно лише одне ML-завдання**.
Причина — NFR-07: Demucs і аналіз одночасно не вміщаються в 6 ГБ, а
паралельний запуск на 4 vCPU не прискорює нічого, лише подвоює пікову RAM.

Правила планування:

1. За інших рівних `analyses:run` обслуговується першим — там чекає людина.
2. **Підвищення пріоритету:** якщо в `analyses:run` є завдання у стані
   `waiting_for_reference`, підготовка потрібної йому пісні піднімається на
   початок `songs:prep` і виконується першою. Інакше користувач чекав би на
   чужі підготовки.
3. Підготовка ніколи не переривається посеред стадії; перемикання можливе
   лише на межі стадій (12.3, ідемпотентність).
4. Якщо `songs:prep` порожня, воркер обслуговує лише аналізи, і навпаки.

### 10.3 Надійність

- **Ідемпотентність**: `job_id` = `analysis_id` або `song_id`; повторна
  доставка того самого повідомлення не створює другу роботу.
- **Пробудження очікувачів**: після переходу `songs.prep_status → ready`
  воркер публікує подію, за якою всі аналізи цієї пісні у стані
  `waiting_for_reference` переходять у `queued`.
- **Зависання воркера**: `XAUTOCLAIM` повертає повідомлення, які висять у
  pending довше 15 хв (для `songs:prep` — 20 хв, стадії довші), назад у
  обробку; після 3 невдалих claim — `failed`.
- **Graceful shutdown**: воркер отримує SIGTERM → дозавершує поточну стадію,
  зберігає прогрес, робить `XACK` або повертає завдання в чергу, і лише тоді
  виходить (`stop_grace_period: 180s` у compose).
- **Максимум 1 активний аналіз на користувача** — решта чекає в черзі.
- `queue_position` перераховується при кожному завершенні завдання і
  розсилається підписаним WS-клієнтам.

## 11. Безпека

Пріоритет наскрізний: безпека важливіша за зручність реалізації. Кожен пункт
нижче — обов'язковий, а не рекомендація.

### 11.1 Периметр

- Cloudflare (безкоштовний тариф) перед VPS — DNS proxy, базовий DDoS-захист,
  приховує реальну IP сервера. Не суперечить "одному VPS" — це зовнішній шар
  перед ним, а не частина compose-стека.
- Публічно відкриті порти лише 80/443 (Caddy) і SSH. Postgres і Redis **не
  публікуються на хост** — тільки внутрішня мережа compose.
- `fail2ban` на рівні VPS проти брутфорс SSH; SSH лише по ключу,
  `PasswordAuthentication no`, `PermitRootLogin no`.
- UFW: deny by default.

### 11.2 Транспорт і заголовки

- Авто-HTTPS через Caddy, HSTS (`max-age=31536000; includeSubDomains`).
- CSP без `unsafe-inline`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`
  з дозволом лише `microphone=(self)`.
- CORS обмежений конкретним доменом фронтенду (не `*`), із credentials.

### 11.3 Завантаження файлів

- Валідація типу/розміру файлів на завантаженні (magic bytes, не лише розширення).
- Ліміти на розмір аудіофайлу (15 МБ / 6 хв) — і на завантаження з YouTube
  (перевірка тривалості перед скачуванням, `yt-dlp`).
- Обов'язкове перекодування через `ffmpeg` у канонічний WAV до будь-якої
  обробки (стадії P1/A1) — це знищує потенційно шкідливі конструкції в контейнері.
- Ім'я файлу від користувача ніколи не використовується як шлях; шлях
  генерується сервером (`uuid`), зберігається поза web-root.
- Зовнішні бінарники (`ffmpeg`, `yt-dlp`) викликаються **списком аргументів**,
  ніколи через рядок shell; таймаут і ліміт пам'яті на процес обов'язкові.
- Обробка виконується від non-root користувача в контейнері без мережевого
  доступу назовні, окрім етапу завантаження з YouTube.
- Ваги моделей монтуються **read-only** і мають зафіксовану контрольну суму,
  що перевіряється на старті воркера: підмінені ваги — це виконання чужого коду.

### 11.4 Застереження щодо YouTube

Завантаження аудіо зі сторонніх сервісів для особистого некомерційного
тестування зазвичай толерується, але порушує ToS YouTube і може зачіпати
авторське право правовласника пісні. Для публічного продакшн-проекту слід
або показати чіткий disclaimer "лише для власного використання", або перейти
на офіційні API з ліцензійним доступом.

**Вимога до реалізації:** функціонал YouTube вмикається прапорцем
`FEATURE_YOUTUBE_IMPORT` (за замовчуванням `true` у продакшн-конфізі), а UI
показує disclaimer перед першим використанням.

### 11.5 Дані і секрети

- Всі секрети — у `.env` (не в git), окремі креденшли для Postgres/Redis.
- `.env.example` містить лише імена змінних і безпечні заглушки.
- Секрети ротуються при будь-якій підозрі на витік; процедура — в `RUNBOOK.md`.
- У логи ніколи не потрапляють: паролі, токени, коди верифікації, email
  повністю (маскується як `s***@gmail.com`), сирі аудіодані.
- Кожен зовнішній вхід валідується на межі (DTO-валідація), а не всередині
  бізнес-логіки.
- SQL — тільки параметризовані запити; конкатенація SQL-рядків заборонена.

### 11.6 Залежності

- Версії залежностей закріплені лок-файлами (`go.sum`, `poetry.lock`/`uv.lock`,
  `package-lock.json`); оновлення — окремим PR.
- У CI: `govulncheck` + `gosec`, `pip-audit`, `npm audit --audit-level=high`,
  `trivy` для образів. Критичні вразливості блокують мердж.

## 12. Вимоги до коду

Три наскрізні принципи: **максимальна безпека**, **DRY**, **ООП**.
Порушення цих принципів — підстава відхилити PR.

### 12.1 Загальні правила

| Правило | Деталі |
|---|---|
| Мова коду | Ідентифікатори, коментарі, повідомлення про помилки, документація в репозиторії — **англійська**. Українською — лише тексти для кінцевого користувача (i18n-файли). |
| Коментарі | Тільки коротко і по ділу, англійською. Коментар пояснює **why**, а не **what**. Заборонено: закоментований код, `TODO` без посилання на задачу, автогенеровані "пояснювальні" блоки. |
| DRY | Будь-яка логіка, повторена втретє, виноситься в спільний модуль. Дублювання правил валідації між шарами й мовами заборонено — джерело істини одне (OpenAPI-схема, спільний конфіг ваг). |
| ООП | Логіка живе в об'єктах із чіткою відповідальністю; залежності передаються через конструктор (DI); залежність — на інтерфейс/абстракцію, не на реалізацію. Ніяких глобальних змінних і синглтонів, окрім явного `ModelRegistry`. |
| SRP | Один тип/клас — одна причина для зміни. Файл > 400 рядків або функція > 50 рядків — сигнал до рефакторингу. |
| Помилки | Ніколи не ігноруються "мовчки". Обгортаються з контекстом і піднімаються на межу, де їх можна обробити. У відповідь користувачу — код і безпечний текст, у лог — деталі. |
| Магічні числа | Заборонені: усі пороги, ліміти, ваги — іменовані константи або конфіг. Стосується й порогів 6.8, 6.15, 6.16. |
| Конфіг | Тільки через env, валідується на старті; застосунок падає з ясним повідомленням, якщо конфіг некоректний (fail fast). |

### 12.2 Go (API)

- Шари: `transport` → `service` → `repository`. Залежності спрямовані всередину;
  `domain` не знає про HTTP, SQL і Redis.
- Інтерфейси оголошуються **на стороні споживача** (`service`), реалізації — в
  `repository`. Це дає DI без фреймворків і тестування з моками.
- `context.Context` — перший параметр кожного методу, що ходить у мережу/БД.
- Помилки: sentinel-помилки в `domain` (`domain.ErrNotFound`), обгортання через
  `fmt.Errorf("...: %w", err)`, класифікація в HTTP-код на рівні `transport`.
- Заборонено `panic` у request-шляху; `recover`-middleware обов'язковий.
- Жодного бізнес-коду в хендлерах: розбір DTO → виклик сервісу → серіалізація.
- Інструменти: `gofmt`, `go vet`, `golangci-lint` (набір: `errcheck`,
  `staticcheck`, `revive`, `gosec`, `ineffassign`, `bodyclose`, `sqlclosecheck`).
- Godoc-коментар обов'язковий для кожного експортованого типу/функції.

### 12.3 Python (ML-воркер)

- Пайплайн будується на абстракції: базовий клас `PipelineStage` з методом
  `run(context) -> StageResult`, конкретні стадії — його нащадки. Додавання
  нової стадії не змінює раннер (Open/Closed).
- Стадія оголошує `required: bool` і `modes: set[Mode]` — раннер сам вирішує,
  чи запускати її в поточному режимі. Умовних `if mode == "mixed"` усередині
  стадій бути не повинно.
- `PipelineRunner` відповідає лише за оркестрацію: порядок, таймаути, повтори,
  паралельну секцію, збереження проміжного стану, логування. Він нічого не
  знає про DSP.
- Профілі ваг і пороги впевненості живуть у `scoring/`, а не всередині стадій.
- Доступ до БД — через репозиторії, а не SQL у стадіях.
- Усі DTO — `pydantic`-моделі; сирих `dict` між шарами немає.
- Повна типізація, `mypy --strict` без ігнорів (виняток фіксується коментарем
  з причиною).
- Детермінізм: фіксовані seed-и, фіксовані версії моделей; один і той самий
  вхід дає той самий бал (з допуском, заданим у тестах).
- Інструменти: `ruff` (lint + format), `mypy --strict`, `pytest`.
- Docstring (Google style) для кожного публічного класу/функції — коротко;
  обов'язково вказати одиниці вимірювання (Гц, центи, секунди, кадри).

### 12.4 Продуктивність ML-коду (обов'язкові вимоги)

Цей підрозділ — прямий наслідок того, що в v1.0 аналіз не вкладався в бюджет.

| Вимога | Деталі |
|---|---|
| Векторизація | Щільні per-frame обчислення — тільки numpy/`numba`/нативна бібліотека. Python-цикл по кадрах — блокер (NFR-17). |
| Один прохід | Кожне представлення сигналу рахується один раз і кладеться в `PipelineContext` (6.9). |
| Гейт по VAD | Кожна per-frame стадія приймає маску вокальних кадрів і не працює по тиші. |
| Обмежені алгоритми | DTW — тільки з коридором і оцінкою розміру задачі наперед (6.7). |
| Потоки | Явна конфігурація, без дефолтів (6.11); у паралельній секції — 1 потік BLAS на задачу. |
| Моделі | Тільки через `ModelRegistry` з `release()`; ваги не вантажаться повторно. |
| Вимірювання | Кожна стадія віддає власну тривалість; PR, що змінює пайплайн, містить у описі до/після з `benchmarks/`. |
| Порядок оптимізації | Спочатку кеш → потоки → профіль → параметри моделей → обсяг аналізу → залізо (6.17). Не навпаки. |

### 12.5 React (фронтенд)

- TypeScript `strict: true`; `any` заборонений (виняток — з коментарем-причиною).
- Структура за фічами (`features/analysis`), а не за типами файлів.
- Мережевий шар один: згенерований з OpenAPI клієнт + обгортка з обробкою
  помилок і рефрешем токена. Прямі `fetch` у компонентах заборонені.
- Серверний стан — TanStack Query; локальний — `useState`/`useReducer`.
  Глобальний стор вводиться лише за доведеної потреби (через ADR).
- Компоненти-презентери без побічних ефектів; логіка — у хуках.
- `null` у балах рендериться як "не вимірювалося" з поясненням, **ніколи** як
  `0` чи порожній прогрес-бар (FR-41).
- Дизайн-токени Tailwind (кольори, відступи, типографіка) визначені один раз;
  довільні значення (`w-[437px]`) заборонені.
- Доступність: семантичні теги, керування з клавіатури, `aria-*` для
  плеєра й піано-ролу, контраст ≥ WCAG AA.
- Інструменти: `eslint`, `prettier`, `tsc --noEmit`, `vitest`.

### 12.6 Заборонені практики (усі мови)

- Секрети, ключі, паролі в коді чи в історії git.
- Логування PII, токенів, вмісту аудіо.
- Конкатенація SQL; виклик shell із інтерпольованим рядком.
- Мовчазне ковтання помилок (`except: pass`, `_ = err`).
- Копіпаста бізнес-правил між Go, Python і TypeScript.
- Закоментований "про запас" код і мертві файли.
- Правки схеми БД повз міграції.
- Усі перф-антипатерни з 6.20.

## 13. Git-процес і коміти

### 13.1 Ідентичність автора

Налаштовується **локально для репозиторію** одразу після клонування:

```bash
git config user.name  "stas"
git config user.email "sizhukstanislav@gmail.com"
git config commit.template .gitmessage
```

Усі коміти в проекті — від цього автора. Перед першим пушем перевірити:

```bash
git log --format='%an <%ae>' | sort -u   # має бути рівно один рядок
```

### 13.2 Формат повідомлення

Conventional Commits, англійською, коротко і по ділу:

```
<type>(<scope>): <subject>

<body — лише якщо потрібно пояснити "чому">

Refs: FR-22
```

- `type`: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`.
- `scope`: `api`, `worker`, `web`, `db`, `deploy`, `docs`.
- `subject`: наказовий спосіб, з малої літери, без крапки, ≤ 72 символи.
- Body — тільки коли рішення неочевидне; пояснює причину, а не перелічує зміни.
- Один коміт — одна логічна зміна. Коміт має залишати `main` у робочому стані.
- Коміти типу `perf` **обов'язково** містять у body цифри до/після з
  `benchmarks/` (12.4).

Приклади:

```
feat(api): add cursor pagination to analyses history
feat(worker): add mixed mode with melody extraction
perf(worker): band dtw search to fixed corridor
fix(worker): release demucs model before whisper stage
refactor(web): extract audio player state into hook
docs(adr): record why ml layer stays in python
```

### 13.3 Чого в комітах бути не повинно

- Будь-яких згадок про генерацію коду асистентами: трейлерів
  `Co-authored-by:` зі сторонніми іменами, рядків `Generated with`,
  `AI-assisted`, емодзі-маркерів, посилань на чати.
- Автоматичних співавторів від IDE-плагінів (перевірити налаштування редактора).
- Довгих машинних "changelog"-описів на 20 рядків — історія має читатись
  як робочий журнал інженера.
- Файлів `.env`, дампів, ваг моделей, аудіо-фікстур > 1 МБ, `node_modules`,
  артефактів збірки.

### 13.4 Хук перевірки (обов'язковий)

`.githooks/commit-msg` — блокує неправильний формат і сторонні трейлери.
Увімкнення: `git config core.hooksPath .githooks`.

```sh
#!/bin/sh
# Validate commit message format and reject third-party attribution trailers.
msg_file="$1"

if grep -qiE 'co-authored-by:.*(claude|copilot|gpt|gemini|assistant|bot)|generated (with|by)|ai-(assisted|generated)' "$msg_file"; then
  echo "commit-msg: attribution trailer is not allowed" >&2
  exit 1
fi

if ! head -1 "$msg_file" | grep -qE '^(feat|fix|refactor|perf|test|docs|build|ci|chore)(\([a-z-]+\))?: .{1,72}$'; then
  echo "commit-msg: expected '<type>(<scope>): <subject>' with subject <= 72 chars" >&2
  exit 1
fi
```

Дзеркальна перевірка в CI (`git log` діапазону PR) — щоб хук не можна було
обійти локально.

## 14. Документація проекту

Над проектом працює **один розробник**, а приймає роботу **тімлід**. З цього
випливають дві задачі документації, і жодна з них не про "гарний вигляд":

1. **Бус-фактор = 1.** Усе, що знає лише розробник, має бути записане, інакше
   проект зупиняється разом із ним.
2. **Тімлід не пише код і не сидить у контексті задачі.** Йому потрібні
   рішення й наслідки, а не переказ дифів.

Тому документації рівно стільки, скільки її реально підтримуватиме одна людина.
Правило одне: **документ оновлюється в тому ж PR, що й код**, який його
змінює. Документація не буває "боргом на потім".

## 15. Тестування

Мета — не відсоток покриття, а впевненість, що зміна не зламала критичні
шляхи: авторизація, черги, підрахунок балів, бюджет часу.

### 15.1 Рівні

| Рівень | Що покриває | Інструменти |
|---|---|---|
| Unit (Go) | сервіси з підміненими репозиторіями, валідація, класифікація помилок | `testing`, table-driven, `testify/require` |
| Unit (Python) | кожна стадія окремо на синтетичних сигналах | `pytest`, `numpy` фікстури |
| Інтеграційні | репозиторії проти реального Postgres, черги проти реального Redis | `testcontainers-go`, compose-профіль `test` |
| Контрактні | відповідність хендлерів `openapi.yaml`, зокрема `null` у балах | схема-валідація у тестах |
| E2E (smoke) | реєстрація → додати пісню → дочекатися підготовки → записати → аналіз → результат | Playwright, 1 сценарій на режим |
| Регресійні (ML) | golden-фікстури: 5–10 с кліпи з відомим очікуваним балом, окремо на `clean` і `mixed` | `pytest`, порівняння з допуском ±3 бали |
| Перф (ML) | бюджет 6.17 на референсному залізі | `pytest-benchmark`, маркер `@pytest.mark.perf` |

### 15.2 Обов'язкові сценарії аналітичної частини

Ці тести існують саме тому, що відповідні місця в v1.0 ламалися або були
непередбачувані:

| # | Сценарій | Очікування |
|---|---|---|
| T1 | Транспозиція: той самий вокал, зсунутий на +3 і −5 півтонів | `key_shift_semitones` визначений правильно; pitch-бал відрізняється не більше ніж на 3 (NFR-20) |
| T2 | Стабільна фальш: вокал, зсунутий на −0.4 півтону | зсув **не** застосовується, бал падає (захист 6.8) |
| T3 | Плавання по тону з нульовою медіаною | зсув не застосовується (перевірка умови по IQR) |
| T4 | `mixed`-фікстура: синтетичний вокал + супровід при SNR 0 дБ і −6 дБ | медіанна помилка F0 < 50 центів (критерій спайку 6.6) |
| T5 | `clean`-режим із супроводом у записі | аналіз успішний, є `ACCOMPANIMENT_IN_CLEAN_MODE`, `confidence` знижена |
| T6 | `mixed`-режим на чистому вокалі | авто-даунгрейд, `effective_mode = clean` (FR-29) |
| T7 | Недоступні аспекти в `mixed` | `breath` і `timbre` = `null`, у `unavailable_aspects` є причина, `overall` порахований за `mixed_v1` |
| T8 | DTW на двох 6-хвилинних записах | пам'ять у межах коридору, час у бюджеті, немає `ALIGNMENT_TOO_LARGE` |
| T9 | DTW на несумісних записах (різні пісні) | чесний `ALIGNMENT_FAILED`, а не випадкові бали |
| T10 | Кеш референсу | другий аналіз тієї ж пісні не запускає жодної стадії P; `cache_hit` у логах |
| T11 | Аналіз поставлено до готовності пісні | статус `waiting_for_reference`, після `ready` автоматично переходить у `queued` (FR-16) |
| T12 | Збій P3 (Whisper) | пісня стає `ready` з `lyrics_available = false`, аналіз проходить (FR-18) |
| T13 | Паралельна секція A9 vs послідовна | однакові бали з точністю до допуску (детермінізм при 6.10) |

### 15.3 Правила

- Тест не ходить у мережу (окрім явно позначених інтеграційних).
- Аудіо-фікстури — короткі, синтетичні (згенерований сигнал із відомим F0 та
  накладеним синтетичним "супроводом"), реальні пісні в репозиторій не комітяться.
- Кожен виправлений баг спершу отримує тест, який його відтворює.
- Цільове покриття: сервісний шар Go ≥ 70%, стадії пайплайну ≥ 60%.
  Числа — орієнтир, не самоціль.
- ML-тести детерміновані: фіксовані seed-и й версії моделей,
  `PIPELINE_PARALLEL_ASPECTS=false` там, де перевіряється точне значення.
- Перф-тести запускаються не на кожен PR (вони довгі), а: на PR, що зачіпає
  `worker/`, і за розкладом раз на добу на `main`.

- Тег `vX.Y.Z` на `main` → збірка образів → деплой на VPS.
- Послідовність: `docker compose pull` → міграції (`goose up`) → `up -d` →

- Міграції завжди зворотно сумісні на один реліз назад (expand/contract),

  `scoring_version` не переписує старі результати, вони залишаються

- Секрети на сервері — у `.env` з правами `600`, власник — деплой-користувач.

## 17. Експлуатація

### 17.1 Резервне копіювання

- Нічний `pg_dump` (сервіс `backup` у compose) → стиснутий дамп у `./backups`,
  зберігання 14 днів локально.
- Раз на тиждень останній дамп копіюється поза сервер (вручну або через
  `rclone`/`restic`) — достатньо безкоштовного bucket-а лише під бекапи. Це не
  порушує вимогу "все на одному VPS для самого застосунку": йдеться виключно
  про страховку на випадок відмови диска.
- Кеш вокальних стемів (`song-cache`) **не бекапиться**: він відновлюваний
  повторним запуском cold path. Це свідоме рішення, зафіксоване в `RUNBOOK.md`
  разом з оцінкою часу на прогрів кешу після втрати.
- **Раз на місяць — навчальне відновлення** з дампа на локальній машині.
  Бекап, який жодного разу не відновлювали, бекапом не вважається.
  Результат перевірки фіксується рядком у `RUNBOOK.md`.

### 17.2 Логи

- Структуровані JSON-логи, рівні `debug/info/warn/error`.
- Обов'язкові поля: `ts`, `level`, `msg`, `request_id`/`job_id`, `user_id` (uuid,
  не email), тривалість для операцій.
- Для стадій пайплайну додатково: `stage`, `mode`, `duration_ms`, `peak_rss_mb`,
  `cache_hit` (NFR-15). Ці поля — основний інструмент розбору повільних аналізів.
- Ротація через `json-file` драйвер: `max-size: 10m`, `max-file: 5`.
- Заборонено логувати: паролі, токени, коди верифікації, повні email, аудіо.

### 17.3 Моніторинг (мінімальний, без окремого стека)

- `/healthz` (живий) і `/readyz` (готовий: БД + Redis доступні).
- Зовнішній безкоштовний uptime-моніторинг пінгує `/healthz`; алерт на пошту.
- Go API експонує лічильники: довжина обох черг, час обробки warm/cold path
  окремо, `cache_hit_ratio` по підготовках, кількість `failed`, розподіл
  `confidence` по завершених аналізах.
- Алерт, якщо медіанний час warm path за добу перевищує бюджет 6.17 більш ніж
  на 25% — це раннє попередження про промах кешу або деградацію заліза.
- Щоденна cron-перевірка вільного місця на диску; алерт при < 15%. Кеш стемів
  росте необмежено, тому окремо контролюється розмір `song-cache`, і в
  `RUNBOOK.md` описана процедура витіснення найстаріших стемів.
- Prometheus/Grafana **не** входять у MVP: обслуговування дорожче за користь
  на цьому масштабі. Рішення переглядається, коли з'явиться другий воркер.

## 18. Етапи робіт і критерії приймання

v1.0 уже реалізовано: E1–E6 закриті (`docs/DEV_LOG.md`), працює один режим
аналізу, одна черга, синхронний пайплайн. v2.0 — не побудова з нуля, а
міграція цієї системи, тому етапи нижче не мають оцінки в тижнях: кожен —
окремий, незалежно мерджований шматок роботи зі своїм критерієм приймання, а
не пункт календарного плану. Порядок фіксований — `M2` і `M3` спираються на
те, що зробив `M1`, а `M3` додатково залежить від власного go/no-go критерію
(6.6). Позначення `M0`–`M5`, щоб не плутати з історичними `E1`–`E6` у
`DEV_LOG.md`. Кожен етап закривається демо і чек-листом приймання від
тімліда.

| Етап | Зміст | Критерій приймання |
|---|---|---|
| M0 | Узгодження ТЗ: `TECH.md` — джерело істини, нумерація ADR виправлена (14.3), `CLAUDE.md` звірений | У `TECH.md` немає посилань на номери ADR, зайняті реальними рішеннями v1.0; таблиця 14.3 відповідає вмісту `docs/adr/` |
| M1 | Продуктивність наявного (одного) пайплайна: `faster-whisper`, спільний кеш STFT/mel (6.9), VAD-гейт (6.5, A2), явна конфігурація потоків (6.11), паралельні аспектні стадії (6.10), дворівневий обмежений DTW (6.7), щільні криві як `bytea` (7.3) — усе **без** зміни архітектури черг | Виміри до/після в `PERFORMANCE.md` на реальній пісні, не синтетичній фікстурі; тести T8, T9, T13 зелені; жоден наявний тест не зламаний; NFR-16, NFR-17, NFR-18 виконані |

Наскрізна вимога до кожного етапу: документи з 14.1, що стосуються етапу,
оновлені, ADR написані **до** початку роботи над етапом (14.3), Definition of
Done (14.5) виконано.

**Точка ухвалення рішення після M3.** Якщо спайк melody extraction не пройде
критерій 6.6, тімлід обирає одне з трьох: звузити `mixed` до одного аспекта
(rhythm), винести `mixed` за межі MVP, або виділити окремий етап на легкий
сепаратор із перерахунком бюджету 6.17. Рішення оформлюється ADR. Тягнути
режим "як вийде" без цього рішення заборонено — це прямий шлях до балів, яким
не можна вірити.

### 20.3 Чек-лист рев'ю для тімліда — `docs/REVIEW_CHECKLIST.md`

```markdown
## Security
- [ ] Input validated at the boundary; no raw user data in paths or SQL
- [ ] No secrets, tokens or PII in code, logs or tests
- [ ] External binaries called with argument lists, with timeouts
- [ ] AuthZ checked: the user can only touch their own resources

## Design
- [ ] Dependencies injected, code depends on interfaces
- [ ] No duplicated business rules across layers or languages
- [ ] One responsibility per type; no logic in handlers
- [ ] Errors wrapped with context, never swallowed
- [ ] Stage declares its modes; no `if mode ==` branching inside stages

## Performance (ML worker)
- [ ] No dense per-frame loops in pure Python
- [ ] Shared feature cache used; no recomputed STFT/mel/chroma
- [ ] Per-frame work gated by the VAD mask
- [ ] DTW is banded, with an upfront size guard
- [ ] Thread counts set explicitly; BLAS threads = 1 inside the parallel section
- [ ] Models go through ModelRegistry and are released
- [ ] Stage durations recorded; perf numbers in the PR description

## Correctness of scoring
- [ ] Unavailable aspects are null with a reason, never 0
- [ ] Weights profile stored with the analysis
- [ ] Key shift applied only under the documented conditions

## Data
- [ ] Schema change ships as a migration, backward compatible one release
- [ ] Indexes cover the new query patterns
- [ ] Dense curves stored as bytea float32, not JSONB

## Process
- [ ] Tests cover the new logic and the reported bug
- [ ] openapi.yaml and affected docs updated in this PR
- [ ] ADR present for architectural decisions
- [ ] Commits follow the convention, single author, no attribution trailers
```
